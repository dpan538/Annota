Annota / features / Ink Transaction Ledger

Ink Transaction Ledger · 笔迹事务账本

Status: preview · version 1.2.1.2 · updated 2026-11-08 persistencelatencystyluscrash recovery

What it is. Pen-up no longer serializes the whole book on the UI thread: a per-book append-only binary ledger records each stroke, and a single whole-book snapshot is written asynchronously.

Problem it solves

Every pen-up synchronously serialized the whole book twice, gzipped and hashed it and committed SQLite on the UI thread. Fast handwriting lost the next stroke's early events (perceived as broken contact).

How it works

Each book has an append-only ledger with CRC frames, page append/replace ops and a custom point codec (zigzag fixed-point with bit-exact float fallback). The UI snapshots page lists, reserves a cursor version and queues a background commit. Serialization, gzip, SHA-256 and SQLite run off-thread; undo/export/close flush first; a read after pen-up waits for the queued snapshot.

Difference from existing approaches

A general database or WAL does not solve ink-specific point encoding, page/version replay and screen/PDF determinism. The ledger is tailored to Annota's Book/Sheet/Mark model and keeps crash recovery and per-stroke undo.

Limitations

  • A crash between snapshot write and ledger trim can duplicate the last snapshot-covered stroke
  • Undo/export/close must flush pending commits
